# floodtwin — a synthetic review fixture

A fictional flood-response digital twin procurement, written to exercise
deliverable-review tooling. **Contains no client material and never will.**
Safe to commit, share, or hand to a third-party model when debugging.

```
requirements.md     fictional RFO — numbered obligations, RFC 2119 modality
deliverable-v1.md   architecture deliverable with 24 planted defects
deliverable-v2.md   generated by make-v2.py — carries the D7 regressions
ground-truth.yaml   every defect and every decoy, with resolving anchors
corpus.yaml         makes the fixture a dossier project, so the real tools run on it
purpose-terms.txt   D9 sweep terms, including two synonym decoys
```

## Where the form comes from

Confidentiality attaches to content, not to document grammar. The substance is
invented; the shape borrows from public conventions:

| Source | Contributes |
|---|---|
| RFC 2119 | MUST / SHALL / SHOULD / MAY — the modality an obligation extractor classifies against |
| NIST SP 800-53 | Structured control-register identifiers and dense cross-referencing |
| ISO/IEC/IEEE 42010 | Architecture-description vocabulary: stakeholders, concerns, viewpoints |
| ISO/IEC/IEEE 29148 | What makes a requirement atomic, unambiguous, verifiable |
| DoDAF / NAF | Viewpoint naming conventions |
| Public tenders (GeBIZ, TED, SAM.gov) | Section/annex structure, evaluation criteria |

The domain is deliberately unrelated to any live engagement. Structural
similarity is generic — components, registers, appendices — rather than a mirror
of a real deliverable's package layout, because that layout can itself be
sensitive.

## What is planted

24 defects across D1–D9 plus one editorial trap, and **6 decoys**. The decoys
are the point: a fixture that scores only recall trains tools to flag
everything. Score precision and recall separately.

Three decoys reproduce failures seen in real review work:

- **DC-003** — a state vector said to be "defined below", enumerated on the very
  next line. A keyword count walks straight into it.
- **DC-005** — a threshold with no value, but disclosed with a named owner, so
  the obligation is *met*. Contrast `GT-D4-001`, where the quantity has neither.
  A tool that treats both identically has misread the standard.
- **DC-006** — identifiers appearing exactly once but defined in place. Singleton
  is a prior for a dangling reference, never a verdict.

## Usage

```sh
./make-v2.py                                              # after editing v1
../../freeze.py --project .                               # freeze, then
../../sweep.py xref  --project . --doc deliverable-v1
../../sweep.py xref  --project . --doc deliverable-v2 --compare deliverable-v1
../../sweep.py vocab --project . --doc deliverable-v1
```

`deliverable-v2.md` is generated, never hand-edited, so every difference between
revisions is a declared regression in `make-v2.py` and the D7 ground truth stays
exact.

## It has already paid for itself

On first run the fixture exposed a false-positive bug in `sweep.py`: the
structural-pointer check recognised only bare `Appendix C` headings as produced
by `.docx` extraction, so against markdown it found **zero** headings and
reported every appendix and section reference in the document as unresolved. The
real corpus never surfaced this, because the real corpus is `.docx`.

That is the argument for building against a surrogate rather than against the
target: a tool validated only on the document it was written for is overfit to
it.
