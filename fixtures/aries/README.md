# aries — humans labelled which edits answer which comment

Peer-review comments paired with the edits an author actually made in response,
human-annotated per comment. AI2, public S3, no credentials,
**ODC-By**. Nothing is committed — `fetch.py` pulls ~1.8 MB of the 327 MB corpus
and verifies a pinned digest.

| | |
|---|---|
| **obligation** | a reviewer's comment on a submitted paper |
| **claim** | the author's rebuttal, asserting what they changed |
| **document** | the paper, before and after |
| **label** | which edits, if any, correspond to that comment |

## Balance, without any sampling

| | |
|---|---|
| not_addressed | **109** |
| addressed | 87 |
| **negative share** | **56%** |

196 comments across 42 papers. That is the natural distribution — no frame
selection, no oversampling. The majority-class baseline is 56%, and any result
from this fixture should be read against it.

## The trap in this dataset, and why only 196 rows are used

The corpus ships **3,350 synthetic labels alongside the 196 human ones** — a 17:1
ratio, and the synthetic majority is unusable here. They were generated by
matching author responses that *quote* the review comment, which means they are
derived from **the claim of compliance itself**. Scoring a tool on whether a claim
is true, against a label built from that claim, measures nothing while looking
like it measures everything.

`fetch.py` filters to `annotation == "manual"` and leaves the rest alone. If a
future version of this fixture reports thousands of rows, that filter has been
lost.

## Why not the live OpenReview API

The same shape is there and the labels are not. OpenReview exposes a per-**review**
score delta and nothing per comment — one number covering a review that raised
five separate points, absent for roughly 80% of reviews, and moving with
co-reviewers' scores rather than with the rebuttal. A tool tuned against it learns
reviewer persuasion and herding, not compliance. That is a validity failure rather
than a noise problem, and more data does not fix it. Access is also gated behind a
browser challenge with a five-requests-per-minute anonymous limit.

ARIES has what the API does not: a human read each comment and each edit and said
which went with which.

## Known weaknesses

- **The label is alignment, not adequacy.** `positive_edits` means the edits
  *correspond* to the comment, not that the comment was answered well. Zero
  aligned edits is a strong negative — nothing in the revision speaks to it at
  all. One or more is **not** a strong positive, and a tool judging sufficiency
  needs its own pass over those 87.
- **The two classes are not symmetric.** Treating them as equally certain
  overstates the positives.
- **n = 196 across 42 papers.** Enough to catch a badly wrong tool, not enough to
  separate two close ones.
- **Machine-learning papers only**, so the prose register is narrow. A tool tuned
  here may not transfer to contracts or engineering specifications.
- **Paper text is a separate 89 MB download** (`s2orc.tar.gz`) and rebuttals a
  190 MB one (`review_replies.jsonl`). This fetcher takes neither: the comment and
  its label are enough to score alignment, and pulling 280 MB to do it would make
  the fixture something people skip.
